# Manager Recommendations Implementation Plan

## Context

Implement all seven pending actions in `/home/colin/dev/data/extract/state/bots/runs/manager/latest.json` as one reliability program: hold and validate the anomalous InfoDengue backfill, preserve partial Workday output without calling it complete, remediate CelesTrak and Melbourne against official retrieval surfaces, add a stateful GDELT circuit breaker, make seven priority sources observable end to end, run bounded OpenActive/Sensor.Community efficiency trials, and stage UK Parliament OData through the existing vetting/review/scheduling gates.

Current constraints that drive the design:

- `orchestration/include/extract_runner.py::run` streams subprocess stdout into `LocalSink`, but non-zero exit currently discards every staged record. That loses the useful Workday tenant output when the provider-wide threshold raises.
- Raw evidence is an atomic `.ndjson` plus `.meta.json`; failures use `.fail.json`. The 4,833,315-record, 3.875-GB InfoDengue artifact is `/home/colin/dev/data/extract/raw/source=infodengue/dt=2026-09-04/infodengue_backfill_full.ndjson`. Its earlier terminated attempt exited `-15` after 446,597 records. The held artifact and its original sidecars must remain byte-for-byte intact.
- Loader discovery currently treats every manifested NDJSON as loadable. `_load.files.status` is load status, not extract completeness; cadence novelty already lives in `_load.cadence_decisions`.
- OpenActive already follows RPDE cursors and checkpoints them at the end of a successful script run. Its experiment must test failure-domain partitioning/replay reduction, not claim cursoring is new. Sensor.Community is a global last-five-minutes snapshot with country/area alternatives and no cursor.
- The City of Melbourne official catalog currently publishes a working JSON download URL for the last-hour dataset. The current v2.1 records URL is the reported 404 path.
- The UK Parliament service document and `$metadata` are live and official. Actual filter/order behavior, page-link shape, and suitability of each date field still require independent source vetting before a staged extractor can be approved.

## Approach

### 1. Guard the InfoDengue artifact before changing behavior

1. Open a controlled loader maintenance window so no scan can select the artifact while hold support is deployed. Before any mutation, query `_load.files` by the exact path above.
   - If absent, continue with the pre-load hold.
   - If already loaded, do not delete raw data, ledger rows, or RAW rows. Record the batch/load IDs, install the hold for future selection, and escalate warehouse remediation as a separate reviewed operation.
2. Record SHA-256, size, line count, original `.meta.json`, related `.fail.json`, and the prior scheduled baseline. Store these values in the hold audit record; do not rename, rewrite, truncate, or copy the 3.875-GB NDJSON.
3. Keep the loader serialized until Step 2 proves that discovery classifies this exact path as held and excludes it from candidates. Resume the loader only after that proof.

### 2. Establish one run-evidence and hold contract

1. Add `orchestration/include/run_metadata.py` as the single parser/validator/manifest builder used by both `orchestration/include/extract_runner.py::run` and `tools/backfill.py::run_unit`; scheduled and backfill artifacts must have identical semantics. Parse at most one reserved stderr line with prefix `VINTAGE_RUN_SUMMARY\t` followed by a JSON object. Non-prefixed stderr remains ordinary logs. Duplicate, malformed, oversized, or internally inconsistent summaries fail the run. Add `run_summary: required` to only the seven affected source YAML files; legacy sources remain compatible and receive `completeness: unknown` until migrated.
2. Make the runner authoritative for transport facts and write manifest schema version 2 with:
   - `status`: `success` for a published manifest, `failed` for a failure marker;
   - `health`: `healthy`, `degraded`, `open_circuit`, or `failed`;
   - `completeness`: `complete`, `partial`, `unknown`, or `failed`;
   - existing source/script/args/timestamps/exit code plus observed `records`, `bytes`, and `duration_s`;
   - `requests`: attempted/succeeded/failed/retries/payload bytes/backoff seconds;
   - `partitions`: attempted/succeeded/failed and a bounded failure list of partition key, error class/status, and retained-record count;
   - source-specific `coverage` and `state_change` objects.
   Validate non-negative counters and `succeeded + failed <= attempted`. Limit detailed failures to 100 while retaining the total failed count. Never infer completeness from a zero record count or ID novelty.
3. Keep transport and source health separate. A process that safely publishes useful partial data has `status: success`, `completeness: partial`, and degraded/failed health. A zero-record exit is complete only when the adapter proves a valid empty source response; otherwise it is unknown. Hard failures with no safe output retain `.fail.json` behavior.
4. Add a sibling `<artifact>.hold.json` convention in `orchestration/include/sinks.py` and loader discovery. The active marker contains schema version, exact artifact and manifest paths, their SHA-256 and sizes, reason, observed validation metrics, actor, and timestamp. `load/loader/discovery.py::scan` must expose held files rather than hiding them; `LoaderService._candidates` excludes them before ledger retry/skip logic and reports `files_held` separately.
5. Add filesystem-only `load/bin/loader hold PATH --reason ... --actor ...` and `release PATH --evidence ... --actor ...` commands. Both require an exact path under the configured raw root and an existing success manifest. Writes are temp-file plus `os.replace`. Release rehashes the artifact and manifest, refuses changed/missing evidence, and atomically renames the active marker to `.hold.released.json` with release metadata so the audit trail survives.
6. Add a read-only `load/bin/loader candidates [--sources ...] [--paths ...]` command that reports held, disabled, already-loaded, attempts-exhausted, young/unmanifested, and pending files without opening the warehouse writable.
7. Propagate manifest evidence through `SinkFile`/`LoadRequest` and add migration-safe `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` fields to `_load.files`: `extract_status`, `extract_health`, `extract_completeness`, `extract_duration_s`, `partition_attempted`, `partition_succeeded`, `partition_failed`, and `extract_metrics JSON`. Preserve existing `status` as load status. Add `files_held` and `files_partial` to `_load.jobs`; keep records/bytes in the existing manifest-record and size columns and novelty/state change in `_load.cadence_decisions`. Do not create a second telemetry store or an operational dbt mart.
8. Update `monitoring/digest.py` to read schema-v2 manifests and hold markers, exclude held artifacts from last-success/freshness/novelty, and display status, health, completeness, records, bytes, duration, partition coverage/failures, and cadence novelty/state change. Unknown values render as unknown, never healthy. Add source-specific comparison metadata in `monitoring/source_types.json` keyed by sink/config source names.

### 3. Bound, deduplicate, validate, and conditionally release InfoDengue

1. Update `extract/scripts/fetch_infodengue.py` to collect deterministic run metrics while retaining one-request-per-municipality behavior. Within each municipality, deduplicate by `(disease, SE)` before emission; the geocode is already fixed for that request, so this avoids a multi-million-entry global set. Track discovered/attempted/succeeded/failed geocodes, emitted and duplicate rows, observed epidemiological week range, request bytes, retries, and bounded failure details.
2. Add explicit CLI/config acceptance limits. For the scheduled rolling ten-week sweep, cap at 75,000 records and 64 MiB. For a single historical year, cap at 350,000 records and 320 MiB. Crossing a cap is a hard non-zero failure before sink publication; municipality failures below the cap produce a partial manifest, not silent completeness. Keep `(geocode, disease, SE)` as the stable identity and compare value changes in `casos`, `casos_est`, `Rt`, `nivel`, `nivel_inc`, `p_rt1`, and `versao_modelo` while ignoring `fetched_at`.
3. Change `extract/sources/infodengue.yml::backfill` from one 2010–2026 unit to `unit: year`, `start: "2010"`, `end: "2026"`, and args `--start-year {yyyy} --end-year {yyyy} --limit 0`. A yearly unit is independently retryable and bounded; do not rerun the full national history as one artifact.
4. Add `tools/validate_infodengue.py`, a streaming validator that reads the source YAML acceptance block and emits a JSON report without materializing the artifact. Validate JSON/envelope/id shape, exact stable-key agreement, duplicate count, geocode coverage, requested year/week bounds, min/max weeks, record/byte caps, per-geocode row distribution, and source-summary consistency.
5. Install the active hold on `infodengue_backfill_full.ndjson`, then validate it and compare it with the previous ~55.7K scheduled batch and the 446,597-record `-15` attempt. Report total/distinct/duplicate keys, overlapping and novel keys, geocode coverage, value changes, and whether `-15` came from the configured timeout or an external termination. Release the held artifact only if its immutable hashes still match and the validator/reviewer evidence establishes intended scope, acceptable duplicates, complete-enough municipal coverage, and bounded semantics. Release makes it pending; loading it remains a separate explicit operation. If validation fails, keep the raw artifact and active hold indefinitely—never “fix” the evidence in place.

### 4. Preserve Workday tenant successes with explicit partial semantics

1. In `extract/scripts/fetch_job_boards.py::fetch_catalog`, retain per-board isolation and `job_boards_lib.common.HttpClient`’s existing three-attempt request policy, four-request Workday concurrency, 150-ms pacing, and bounded `Retry-After`. Do not add an outer retry that multiplies those attempts.
2. Produce a deterministic final summary for every Workday run: attempted/succeeded/failed tenants, per-tenant final error/status and retry count, retained records, and provider threshold result. Any failed tenant makes completeness partial. Preserve the existing provider-outage threshold (all tenants fail, or at least three and at least 80% fail) as `health: failed`; smaller failure sets are `health: degraded`.

Thus a 703/875 failure run retains its 218,150 successful records but can never be represented as provider-complete.
4. Ensure loader propagation preserves `extract_completeness: partial` and tenant counts while ordinary path/batch ledger idempotency prevents the same artifact from loading twice. Monitoring must alert on provider health/completeness independently of transport success.
