# Bot Workflow Hardening Plan

## Context
Implement the full hardening program identified in the current bot-workflow assessment: restore Airflow 3 compatibility, establish one authoritative state path, make all run outcomes typed, enforce coherent deadlines and retries, reduce model workload, add queue backpressure, unify mutation governance, and make manager evidence freshness observable. The intended end state is an event-driven, auditable workflow in which deterministic control-plane decisions are cheap, model work is bounded, and every mutation follows one review lifecycle.

## Learned findings
- `orchestration/dags/bots_dag.py:_run` calls `bots/provider_dashboard.py:schema_ready` inside task execution; that function uses `airflow.utils.session.create_session`, which Airflow 3 rejects in task context. The same defect exists in report projection, manager backlog/reconciliation, execution claim/finalization, the minute dispatch/maintenance DAG callables, and `bots/agent_context.py:_airflow_failures`.
- The provider already has a FastAPI server boundary at `/bot-dashboard/api`, standard Airflow bearer authentication, strict Pydantic request patterns, transactional service functions, and a task/execution/event schema. Add machine-facing routes there; do not create another database access mechanism.
- `orchestration/airflow.env` currently enables the dashboard but leaves UI writes and the executor disabled. Dashboard enablement must not imply that task workers may write through ORM, and internal report persistence must not depend on the UI write switch.
- Dashboard projection disables legacy report persistence, while `bots/agent_context.py:_reports` still reads only the external filesystem report tree. A one-time import plus API-backed reads is required before filesystem reports stop being authoritative.
- Runner-generated `skipped` and `busy` bodies are prose, but dashboard projection parses JSON for JSON-output bots. The provider's `RunReport` identity also omits `try_number`, so retries cannot be represented independently.
- Provider and Airflow deadlines are equal for `source_discovery` and `failure_triage`; Airflow can kill the outer task before provider timeout handling and fallback. Provider code currently classifies command/network timeouts as `ProviderBusy`.
- `source_discovery`, `cadence_review`, and `failure_triage` prompts are approximately 74 KB, 69 KB, and 53 KB respectively.
- The repository contains both direct review-package promotion (`reviewer`) and dashboard-admitted PR execution (`task_executor`/`pr_reviewer`) without one documented authority boundary. The dashboard execution path does not yet create a branch or pull request even though finalization requires `Execution.pr_number`.
- Task code cannot access Airflow's execution JWT directly. Worker-to-provider calls therefore need a normal Airflow service identity obtained from secret configuration; model subprocesses and the confined sandbox must continue receiving filtered environments without that credential.

## Approach

### 1. Establish an Airflow-3-safe provider service boundary before changing bot callers

- In `orchestration/provider_bot_dashboard/src/airflow/providers/vintage/bot_dashboard/api_models.py`, add strict, `extra="forbid"` request/response models for the machine API. Mount a new `/api/internal` router in `api.py`; every route must require the configured service username through Airflow's existing `get_user` bearer authentication, run `_schema_guard`, enforce the existing 1 MiB request middleware plus the configured report/diff bounds, and ignore the UI-only `write_enabled`/CSRF policy. Add provider option `internal_user` with default `bot-worker`; no internal route accepts browser cookies as machine authentication.
- Add `bots/provider_dashboard.py:DashboardClient`. It reads `AIRFLOW__API__BASE_URL`, `BOT_DASHBOARD_API_USERNAME`, and `BOT_DASHBOARD_API_PASSWORD`, obtains a short-lived JWT from the existing `POST /auth/token`, sends it only as an `Authorization: Bearer` header, applies bounded connect/read timeouts from the parent run deadline, redacts response errors, and retries authentication once on 401. Keep the credential out of XCom, logs, command-provider environments, and sandbox environments. When the dashboard is enabled, an unavailable API is a classified control-plane failure; there is no filesystem fallback.
- Add `bot-worker:op` to the rendered Simple Auth user list for this deployment and generate its password into both the Simple Auth password file and gitignored `orchestration/airflow.secrets.env` from `orchestration/setup/02_database.sh`; extend `airflow.secrets.env.example`, `config.example.env`, `airflow.env.template`, and `setup/render_config.sh` with the username/password/config tokens. Existing deployments must merge rather than replace the generated password JSON. For non-Simple auth managers, document the equivalent service account with read/write access only to `bot__*`, `bot_dashboard__dispatch`, `bot_dashboard__maintenance`, and the configured Git connection.
- Implement these server-side operations by reusing the existing session-taking functions in `projection.py`, `service.py`, `execution.py`, `review.py`, and `maintenance.py`; no task-side module may import `airflow.models`, `airflow.utils.session`, SQLAlchemy models, or provider service/domain functions afterward:
  - `POST /api/internal/runs/report`: validate and persist one universal run envelope.
  - `POST /api/internal/runs/claim-budget`: atomically create or return one logical-task deadline keyed by DAG/run/task/map, before any context or model work.
  - `POST /api/internal/runs/query`: return bounded, deterministic report history/latest-useful metadata for named bots, date window, outcomes, and limit.
  - `GET /api/internal/manager/context?days=7`: return bounded task backlog plus fresh/stale specialist evidence.
  - `POST /api/internal/manager/reconcile`: reconcile the stored manager report identified by DAG/run/task/map/try.
  - `GET /api/internal/airflow/failures?hours=24&limit=100`: run the current `DagRun`/`TaskInstance` query server-side and return bounded task metadata; log tails stay capped at 30 lines/3,500 characters.
  - `POST /api/internal/executions/claim`, `PUT|GET /api/internal/artifacts/{sha256}`, `POST /api/internal/executions/publish`, and `POST /api/internal/executions/finalize`: own admission, content-addressed artifact transfer, PR publication, report/review finalization, and immutable lifecycle events.
  - `POST /api/internal/dispatch/claim` and `/api/internal/maintenance/run`: own the ORM work currently called directly by `provider_bot_dashboard_dags.py`; responses remain bounded native trigger argument lists plus metrics.
- Replace every call in `bots/provider_dashboard.py`, `bots/agent_context.py:_airflow_failures`, `orchestration/dags/bots_dag.py`, and `orchestration/dags/provider_bot_dashboard_dags.py` with `DashboardClient`. Remove `schema_ready()` from task execution; `/health` remains an operator check while every internal endpoint independently guards the schema. Remove the `all_done` manager/admission ORM finalizer tasks after report submission/finalization becomes one idempotent server call.
- Keep direct ORM only in the FastAPI server, provider migration/administrative CLI, and provider domain functions invoked by those boundaries. The installed wheel mirrors `orchestration/provider_bot_dashboard/src`, so bump the provider version, rebuild the UI assets and wheel, install that wheel, and run Airflow/provider migrations before switching DAG callers.

### 2. Make one typed run envelope, one deadline, and classified retry behavior

- In provider `report_schemas.py`, define runner-owned `RunEnvelopeV1` with exactly:
  - `envelope_version: 1`;
  - `identity: {bot, dag_id, run_id, task_id, map_index, try_number}`;
  - `timing: {started_at, finished_at, deadline_at, duration_ms}`;
  - `outcome: succeeded|skipped|capacity_unavailable|timed_out|failed`;
  - `retry_class: none|capacity|transient|terminal`;
  - `reason_code`;
  - nullable `failure: {class, code, fingerprint, detail}` where detail is bounded/redacted and the fingerprint excludes timestamps, UUIDs, run IDs, attempts, durations, and absolute paths;
  - nullable `selected_model`;
  - `attempts[]` entries `{ordinal, alias, provider, started_at, finished_at, duration_ms, outcome, reason_code, fallback_used, input_tokens, output_tokens, total_tokens}`;
  - `context: {sha256, byte_count, build_ms}`;
  - nullable `payload_schema` and bot-specific `payload`.
  Bot-specific schema validation runs only for `outcome=succeeded`; skipped, capacity, timeout, and failed envelopes require `payload=null`. Bound canonical envelopes to 256 KiB and failure detail to 8 KiB after redaction; reject rather than truncate schema-valid bot payloads. The API response/XCom projection contains only report row ID, envelope digest/bytes, outcome, retry class, failure fingerprint, and execution identity.
- Add forward-only `0003_workflow_hardening.py`. Add `RunBudgetClaim` keyed by `(dag_id, run_id, task_id, map_index)` with immutable `deadline_at`. Extend `RunReport` with `try_number`, outcome/retry/failure/timing/context/attempt-metrics columns; change uniqueness to `(dag_id, run_id, task_id, map_index, try_number)` and reference the logical budget claim. Backfill old rows with try 1 and map old `ok`, `skipped`, and `busy` statuses to the new outcomes without deleting history. Extend `Task` with nullable `source_bot`, broaden `source` to `manager|manual|specialist`, extend `Revision` with bounded JSON `evidence`, `verification_commands`, `allowed_path_globs`, `resource_keys`, and `follow_up_bots`, and extend `Execution` with `executor_deadline_at`, `review_deadline_at`, base/artifact/verification fields, review-publication fingerprint/time, and terminal failure metadata. Add an `Artifact` table keyed by SHA-256 for byte count, media type, creation/expiry, and owning execution; bytes live in the provider-owned content-addressed spool, not the metadata DB.
- Replace `bot_runner.BotRun` with the typed envelope/result builder and remove report/context bodies from its public/XCom representation. Canonicalize context before prompt substitution and record only its hash/size/time. `POST /runs/report` sanitizes the payload with the existing redactor, validates the named payload schema, calculates canonical payload/envelope hashes, persists one row per Airflow try, and treats identical replay as success while rejecting a different body under the same identity.
- Add `RunBudget` in `bots/bot_runner.py`. Before context construction or model work, call `/runs/claim-budget` with the logical task identity and configured total; the server atomically creates `deadline_at=now+timeout_minutes` or returns the existing claim and rejects a changed configured total. Initialize the monotonic budget from that absolute deadline on every Airflow try, reserving `cleanup_margin_seconds`; a retry with no remaining time submits `timed_out/deadline_exhausted` without context or model work. Thread the deadline through context commands, gate evaluation, inference-slot/preflight work, every fallback, JSON validation, subprocess/network calls, and API persistence. Every child timeout is `min(local_cap, remaining_budget)`; fallback candidates share the deadline and start only after explicitly fallbackable capacity/transient/invalid-completion failures while time remains.
- In `bots/providers.py`, return `ProviderResult(text, duration_ms, input_tokens, output_tokens, total_tokens)` and split failures into `ProviderBusy`, `ProviderTimeout`, `ProviderTransient`, and `ProviderTerminal`, each with stable code and `fallbackable`. Map slot exhaustion, command exit 3, rate-limit text, and HTTP 429/503 to busy/transient; map actual subprocess/socket deadline expiry to timeout; map missing executables, malformed configuration, non-retryable 4xx, response-shape errors, and credential absence to terminal. Never classify a process that ran until its deadline as busy. Bound and redact diagnostics; never log prompts, rendered argument values, or environments.
- Strictly validate all bot and model YAML in `load_bot`/`load_models`: known keys and types, context/gate/output shape, positive timeouts/limits, named schema implies JSON, trigger existence, provider-specific endpoint/argv requirements, default/assignment aliases, declared capabilities, and fallback capability compatibility. Add exact bot keys `model_budget_minutes`, `cleanup_margin_seconds`, `capacity_policy: skip|retry`, and `retry_on: [capacity, transient]`; executor definitions may additionally set `publication_budget_minutes`. Require `sum(context timeout caps) + model_budget_minutes*60 + cleanup_margin_seconds <= timeout_minutes*60`; fallbacks do not add another budget.
- Replace regex gates with typed JSON gates: `{context, path, operator: equals, value, reason_code}`. Implement dotted-object lookup and only `equals` initially; migrate every existing `pending_count/backlog_count/failure_count` gate and discovery's boolean backpressure gate. A valid no-work gate returns a green `skipped` envelope so downstream deterministic trigger checks may still run.
- In `bots_dag._run`, persist every envelope before translating it to Airflow behavior. Return `succeeded`/`skipped`, plus `capacity_unavailable` only when `capacity_policy=skip`, as bounded green XCom metadata; raise `AirflowException` only when `retry_class=capacity|transient` is selected by `retry_on`, and raise `AirflowFailException` for terminal outcomes, including final deadline exhaustion. Set one Airflow retry (`retries: 1`) for model DAGs; a provider timeout may use a fallback only while the current `RunBudget` still has time, but an exhausted attempt is never retried with a fresh full budget. Use `capacity_policy: skip` for recurring specialists and `capacity_policy: retry` for manager, task executor, and PR reviewer. Remove `busy_is_error`.
- Apply these concrete internal budgets through the exact keys above; set each generated PythonOperator `execution_timeout` to `timeout_minutes + 2 minutes` so scheduler/worker startup and final envelope persistence cannot lose the typed timeout: discovery 30m total/20m model/5m context/120s cleanup; vetting 35m/25m/5m/180s; scheduling 35m/25m/5m/180s; cadence 25m/15m/6m/120s; triage 30m/20m model/5m context/180s cleanup; analytics 45m/30m/10m/180s; manager 30m/20m/5m/180s; executor 60m/40m model/10m publication/5m other; PR reviewer 45m/30m model/5m publication/5m other. Mirror the executor task's budget claim into `Execution.executor_deadline_at` and its later reviewer task's independent claim into `Execution.review_deadline_at`; retries and lease recovery never reset either value.
- Update `models.example.yml` and the active gitignored `models.yml` to `concurrency.max_active: 2`, with `max_concurrency: 1` on the local endpoint and each command alias. Configure `manager: [plan_cli, openrouter]` only when `OPENROUTER_API_KEY` is present; do not create tool-less fallbacks for web/repository roles. Align OMP `--max-time` and provider caps to the model budgets above. Add startup validation that reports unavailable optional fallbacks without weakening required capabilities.

### 3. Make provider reports/events authoritative and migrate legacy state once

- Change `bots/agent_context.py:_reports` into a bounded `DashboardClient` query; all discovery/vetting/failure/manager history, active task exclusions, and latest specialist inputs come from `RunReport`, `Task`, and `Execution`. A dashboard/API error becomes an explicit context failure and cannot look like an empty healthy queue. Scheduled live bot DAGs are created only when the provider is installed and enabled; `run_bot --dry-run` remains available without persistence, while a non-dry CLI run requires the API unless explicitly invoked with new `--ephemeral`.
- Add `bot-dashboard import-legacy --runs-root PATH --reviews-root PATH [--check]` as an administrative, one-time CLI operation. In CLI-only `legacy_import.py`, refactor the existing ownership/mode/size/path checks into a descriptor-relative, `O_NOFOLLOW` reader parameterized by an explicitly configured root, allowlisted suffixes, and per-kind caps; use it for report (`.json`/`.md`, 256 KiB), manifest (`.json`, 256 KiB), and patch (`.patch`, configured maximum diff size) inputs. Treat every manifest path as an untrusted relative reference under the supplied reviews root; reject absolute paths, `..`, cross-device files, symlinks, and manifest-provided roots. For each valid report, derive `dag_id=legacy__<bot>`, `run_id=legacy__<sha256(relative-path)>`, `task_id=import`, `map_index=-1`, and `try_number=1`; take both timestamps from the validated filename timestamp or file mtime with `legacy_timestamp_inferred`, and reject digest/identity disagreement. It never applies a patch or creates an active execution.
- Add `bot-dashboard inspect-run --dag-id ID --run-id ID --task-id ID [--try-number N]` as a read-only administrative command returning the same body-free projection metadata plus stored outcome/timing/failure fields; deployment smoke uses it instead of querying ORM or following report paths.
- During deployment, pause the old `bot__reviewer` and the four legacy writing bots, snapshot the legacy state root, run/import/verify counts and hashes, then switch all bot definitions together. An old package already named by a reviewer report is recorded as historical and reconciled against the current checkout but never reapplied; missing/malformed/unverifiable packages become human-attention tasks. Preserve the read-only quarantine until every imported task is dismissed or re-executed.
- After verified cutover, remove `_write_report`, `prune_reports`, review-package/worktree creation/reset/apply/cleanup, `BotRun.report_path/review_package`, `_pending_review_packages`, runtime `legacy.py`, `legacy_reports_root`, and normal XCom/path reconciliation. Filesystem report/package data remains only as quarantine backup, never as a gate or manager input.
- Server retention is outcome-aware: successful payloads 3,650 days, failures/timeouts 365 days, and payload-free skips/capacity outcomes 7 days. Skips never replace the latest useful payload in manager/history queries.

### 4. Compact contexts, add backpressure, and separate data failures from bot health

- Add `context_schema_version: 1`, `context_kind`, `generated_at`, and `as_of` to every context. Keep deterministic key/list ordering and explicit error fields; never turn API, digest, warehouse, or cadence-command errors into empty healthy arrays. Enforce canonical serialized context limits before prompt substitution—discovery 32 KiB, vetting 24 KiB, scheduling 24 KiB, cadence 32 KiB, triage 48 KiB, analytics 32 KiB, manager 96 KiB—using the item limits below plus `{truncated,total_count,returned_count}` metadata; fail context construction if mandatory selected evidence alone exceeds its cap.
- `discovery_context`: expose existing sources/scripts, `vetting_pending_count`, `vetting_inflight_count`, `backpressure_limit: 5`, and `backpressure`. Reduce history to the last 50 unique normalized queries, domain counts, and at most 100 summaries `{slug,title,domain,viability,status,source_report_id}`; retain the seed count but not full proposal bodies. Change discovery to `17 */6 * * *`, emit at most two proposals, and skip the model when backpressure is true.
- `vetting_context`: sort unresolved candidates by viability high/medium/low, report creation time, then slug; expose queue counts and exactly one selected full proposal. The prompt must vet `selected.slug` and may not choose another. Terminal decisions are `recommended`, `rejected`, `blocked_user_token`, or `needs_research`; a recommendation contains a task proposal rather than changed files.
- `scheduling_context`: replace staged-package assumptions with exactly one selected merged staged extractor lacking source configuration or one active scheduling task. Include only script/path/slug, originating vetting report/task reference, source count, minute-field load, and scheduling rules. The prompt plans that exact item and emits no file claims.
- `cadence_context`: merge managed, flagged, and rotating samples by source; include every flagged source plus at most 12 rotating sources with only the digest fields consumed by the prompt. Bound cadence decision text to 40 lines/12,000 bytes. Add `review_required`, true when any source is flagged, a cadence decision is newer than the last successful audit, or no successful usefulness audit exists in 24 hours; keep the four-hour detector schedule but gate the model on false.
- Move the Airflow failure query to `/internal/airflow/failures`. Add one deterministic fingerprint helper shared by runner/provider/context code, grouping failures by origin/component/task/error class/code/normalized detail. Cap each group at 10 occurrence run IDs, each tail at 3,500 bytes, sink markers at 20, selected groups at 10, and preserve `remaining_after_batch`. Exclude `bot__*` and `bot_dashboard__*` from model triage; expose those envelope failures as deterministic `bot_health` in dashboard and manager context so triage cannot consume itself.
- `analytics_context`: retain one-source priority but expose only selected source columns/paths/issues, counts, and active dashboard tasks identified by `resource_keys`; remove full source/model inventories and task bodies from the prompt. Warehouse/sync/manifest failure is an explicit hard context failure.
- Add explicit `freshness_sla_minutes` to bot YAML: discovery 390, vetting 420, scheduling 420, cadence 300, triage 90, analytics 1,440. The manager API returns for each specialist both `latest_run` and `latest_useful_payload`, with report/run IDs, outcome, observed time, age, SLA, `freshness: fresh|stale|missing|failed|not_due`, digest, and bounded payload. Manager context includes `stale_agents`, `missing_agents`, `failed_agents`, `freshness_ok`, and `bot_health`; analytics is `not_due` only when its deterministic backlog is zero.
- Replace `manager_v2` with `manager_v3`, retaining all plan/deferred/approval invariants and adding required `input_freshness {as_of,freshness_ok,stale_agents,missing_agents,failed_agents,max_age_seconds}`. A stale/missing/failed required specialist forces `status=degraded_evidence`. Update manager prompt, bot schema, reconciliation, provider/UI types, and tests in one clean cutover.

### 5. Convert every specialist into a strict read-only recommendation producer

- Add named Pydantic schemas for every specialist instead of `required_keys`. Reuse one strict `TaskProposalV1` in vetting, scheduling, cadence, triage, and analytics. It contains bounded `recommendation_key`, `title`, existing task `category`, priority, `planned_resolution`, `why_now`, `expected_benefit`, `risk`, `rollback`, `verification_commands` as argv arrays (no shell strings), `allowed_path_globs`, `resource_keys`, `follow_up_bots`, `suggested_executor: junior|senior|staff`, `reviewer_required: true`, and evidence references/summaries. The executor uses the intersection of task globs and repository policy. Keep `ManagerPlanItemV3` as the strategic human-approval shape inherited from v2; `reconcile_manager` maps it to a Revision with no executable argv/path globs until a human supplies them before assignment.
- Keep discovery as research-only `SourceDiscoveryV2`. Convert:
  - vetting to `SourceVettingV2`, remove `script`, `files_changed`, and claims of staged verification; require one `task_proposal` for `recommended`;
  - scheduling to `SourceSchedulingV2`, replace `changes` with implementation `plans` and task proposals;
  - cadence to `CadenceReviewV2`, retain source reviews/issues and add task proposals only for evidence-backed adjustments;
  - triage to `FailureTriageV2`, remove repair/logging edits and `files_changed`; actions become `task_proposed|observe|human_review`, keyed by failure fingerprint;
  - analytics to `AnalyticsEngineerV2`, replace changed models/files with one-source implementation plans and task proposals.
- Remove `workspace_lock`, runner `review_required`, write capabilities, and `triggers: [reviewer]` from those bot YAML files. Give research/audit bots only read/web capabilities; add a `repository_execute` capability/profile for analytics and other specialists that must run read-only probes, with OMP tools restricted to `read,grep,glob,bash` and no edit/write tool.
- On successful report submission, server-side `reconcile_recommendations` idempotently creates/revises `source=specialist` tasks by globally unique `<source-bot>-<recommendation-key>`, records source run/report/evidence, and applies existing category policy. Default remains `manual`; `auto_accept` changes state only, and `auto_delegate` may create an execution only through `service.start_task`. Models never directly admit themselves.
- Extend task patch/UI forms so a human can edit `verification_commands`, `allowed_path_globs`, `resource_keys`, `follow_up_bots`, and reviewer policy before assignment. `start_task` rejects bot assignment when planned resolution, bounded argv verification, nonempty task path policy, or executor profile is missing; human-only strategic tasks may remain accepted without those fields.
- Remove `bots/reviewer/` and its model assignment/profile. The remaining topology is six read-only specialists plus manager, with manual `task_executor` as the only writer and `pr_reviewer` as the only reviewer.

### 6. Complete the admitted executor → artifact → PR → review lifecycle

- Keep `service.start_task()` as the sole admission boundary. Make `claim_pending()` deterministic by `(created_at,id)`, keep `skip_locked` and bounded leases, and require exact target DAG IDs. Trigger conf remains only `{execution_id, revision}`; the executor/reviewer logical task claims its immutable deadline when its Airflow task first starts, so dispatcher queue delay does not consume execution budget.
- At executor claim, server-side trusted code resolves the configured Git repository/base branch, records the immutable base SHA, creates a clean source tar artifact, and returns its digest plus path policy, task proposal, verification argv, and deadline. `run_admitted()` downloads it through the authenticated artifact API, validates digest and safe extraction, initializes a credential-free local baseline, and invokes only the configured root-owned sandbox launcher. Define strict `ExecutorAdmissionV2` and `ExecutorResultV2` schemas: the trusted parent creates a mode-0700 temporary work directory, safely extracts the tree below it, writes mode-0400 `admission.json`, and invokes a fixed executable with exactly `--protocol v2 --workdir <dir> --admission <dir>/admission.json --result <dir>/result.json`; no user/model value becomes an option or executable. The launcher rejects extra argv, confines all writes to `workdir`, and writes one mode-0600 result atomically. The parent accepts only that regular no-follow result file and always removes the work directory.
- The sandbox receives the plain tree, admission JSON, profile, and remaining deadline; it receives no `.git`, parent paths, Airflow, sockets, service/Git credentials, or unrestricted network. `ExecutorResultV2` contains only the typed outcome plus bounded `TaskExecutorV2` report. Verification commands come from the human/policy-admitted task, run in the same confinement after edits, and cannot extend the parent deadline. The trusted parent—not the launcher or model—computes `git diff --binary` from the baseline, validates allowed/denied globs, file count and diff size with `validate_changed_paths`, then creates `VerificationManifestV1` containing task/execution/revision/base SHA, sorted changed paths, patch digest/bytes, source report reference, and checks `{name,argv,exit_code,observed,observation_sha256}`; it verifies all digests before uploading patch and manifest by content hash.
- Implement provider-owned `publish_execution_change`: materialize a fresh trusted clone at the recorded base SHA, apply the exact artifact, commit with the service identity, push deterministic branch `bot-dashboard/<task-id>/<sequence>-r<revision>`, create or recover the draft PR through `GitProvider.create_change`, reread it, and atomically persist provider/repository/branch/base/PR/service-account/trusted-head identity plus `change_published`. Git credentials exist only in the server-side child environment, never argv/logs/artifacts. Replays compare base/patch/head and return the existing identity; mismatches are terminal.
- On `no_change`, persist the verification manifest and move the task to `ready` without Git mutation. On blocked, policy, permanent, or deadline outcomes, persist the classified terminal result and create no PR. Fix the missing `secrets` import while replacing the current incomplete `finalize_run` branch.
- Create a `pr_reviewer` admission only after PR identity is durable. Its claim returns the exact immutable PR/head identity, task/revision, diff/source artifact, executor report digest, and verification manifest. The reviewer remains read-only and cannot approve/merge/apply through provider APIs. Replace comment posting with an idempotent `GitProvider.upsert_comment(marker, body)`, using deterministic marker `bot-dashboard-review:<execution-id>:r<revision>` and provider list/update APIs, then record the comment fingerprint/time before finalizing the review event.
- `maintenance.sync_provider()` remains the sole provider observer: revalidate provider/repository/author/base/head on every observation; classify network failures as transient; mark identity/head drift or closed-unmerged PR terminal/human-attention; move `in_review` to `ready` only when the required verdict is approved at the trusted head and the PR is open/non-draft or merged. It records merge but never merges. Existing human comment/evidence plus `transition_task()` remains required for `completed`.
- Add provider options `artifact_root` and `artifact_retention_days` (default 365), rendered as `AIRFLOW__BOT_DASHBOARD__ARTIFACT_ROOT="$EXTRACT_DATA_ROOT/state/bots/artifacts"` and `AIRFLOW__BOT_DASHBOARD__ARTIFACT_RETENTION_DAYS=365`. Store patch/source archives there as mode-0600, content-addressed files derived only from validated SHA-256; use atomic no-follow writes and DB ownership/retention, and never prune an artifact referenced by a nonterminal task or open PR. The DB artifact row is authoritative. Executor enablement remains fail-closed until the configured external launcher satisfies the existing ownership/confinement/network assertions; no unconfined fallback is added.

### 7. Rewire schedules and event routing around queues, not reviewer packages

- Final schedules: discovery `17 */6 * * *`; vetting `47 */6 * * *`; scheduling `47 1-23/6 * * *`; cadence detector `37 */4 * * *`; triage `7 * * * *`; analytics `27 */4 * * *`; manager `57 9 * * *`; executor and PR reviewer manual. Remove the legacy reviewer schedule entirely.
- Keep discovery → vetting as the only specialist report trigger. Vetting capacity exceeds discovery because discovery emits at most two proposals four times daily while vetting has four backstops plus discovery events. Do not use recursive self-trigger run IDs.
- Report submission creates specialist task proposals immediately; accepted/delegated work reaches executor only through the minute dispatcher. ## Assumptions & contingencies

- The provider dashboard lifecycle is the selected authority: recurring specialists become read-only, `task_executor` is the only writer, `pr_reviewer` is the only reviewer, and humans remain the only merge/completion authority. Do not preserve direct shared-checkout application as a compatibility path.
- Dashboard-backed scheduled operation is fail-closed. If the provider wheel, schema, internal service identity, or API is unavailable, omit/pause live bot DAGs and expose the health code; allow only dry-run or explicit `--ephemeral` CLI execution. Never silently resume filesystem report or review-package authority.
- The local Simple Auth deployment may use `bot-worker:op`. If another auth manager is configured, provision an equivalent least-privilege service identity and point the same username/password environment variables at `/auth/token`; if that cannot be done, leave the dashboard and bot DAGs disabled rather than adding an unauthenticated/shared-secret endpoint.
- The root-owned sandbox launcher and allowlisted model-gateway network policy are external security prerequisites. Implement and fully test protocol v2 with a fake launcher, but retain `executor_enabled=False` until the real launcher passes current owner/mode/confinement assertions. No implementation may weaken those assertions to complete the smoke test.
- GitHub and GitLab remain supported through the existing provider abstraction; implement deterministic publish/comment idempotency for both. If a configured provider cannot supply branch/head/author identity and comment listing/update, fail that execution with `provider_capability_missing` rather than using a less-verifiable path.
- No capability-equivalent second model currently exists for most tool-using roles. Configure only the manager fallback when its credential is present; capacity limits and honest failure are preferable to a chat-only model impersonating web/repository access.
- If no converted gated bot has zero work during deployment smoke, use the permanent integration fixture against the deployed API instead of changing operational state to manufacture an empty queue. Legacy imports with missing or unsafe artifacts become proposed human-attention tasks and remain quarantined; they are never dropped or applied automatically.
